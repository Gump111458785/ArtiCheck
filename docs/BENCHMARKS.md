# Benchmark 与结果协议

本文汇总评测任务口径和可公开复查的结果。完整流水线的模型对照与数据划分见 [Supervisor 后训练与评测](SUPERVISOR_TRAINING.md#evaluation)。

## 1. 评测覆盖

### ArtiCheck-Claims：主张级缺陷评测

任务覆盖指标计算、训练与测试划分、基线设置。协议以至少 50 个独立仓库和 1,000 条人工复核主张为规模目标，公开文档只报告附有数据与运行记录的结果。

每个原始仓库保留经核验的 clean 版本，针对可判定缺陷建立注入版本，并收录能取得独立证据的真实问题。注入缺陷与自然缺陷分开报告；不能把注入实验结果直接解释为真实论文的缺陷发现能力。缺陷比例和难度分布随数据版本记录。

按原始仓库谱系分组，沿用当前 80/10/10 的划分协议。所有复制品、分支、注入版本与关联主张共享 repo_id；对同源数据不能通过改名获得独立测试样本。正式版本需保存 commit、probe、标签来源、审核记录和 split 清单，且需确保验证集与测试集均包含正负主张。

质量协议要求两名审核人独立标注，分歧由第三人裁定。训练数据可包含经审核的教师轨迹；验证与测试真值只用于评测。

### CORE-Bench：公开的计算复现基准

[官方仓库](https://github.com/siegelz/core-bench)描述的规模为 90 篇科学论文、270 个任务。任务要求阅读说明、处理代码和依赖、运行实验并回答结果问题，适合衡量执行与结果读取能力。

按 Easy、Medium、Hard 分层，沿用官方任务判定与结果聚合口径。兼容入口见 [HAL Harness](https://github.com/princeton-pli/hal-harness)。子集结果须注明任务 ID、规模和筛选标准。

该数据不直接给出“某实验主张是否存在科学缺陷”的标签。若额外注入缺陷，所得数据必须另命名为派生集，并独立核验真值，不能与原生 CORE-Bench 混为一谈。

### PaperBench JudgeEval：公开的判定质量基准

[JudgeEval 官方说明](https://github.com/openai/frontier-evals/tree/main/project/paperbench/paperbench/judge/judge_eval)提供 5 份带人工预期评分的 submission，在 rubric 二元节点上计算 accuracy、precision、recall 和 F1。它独立于 PaperBench 的复跑阶段；JudgeEval 本身不运行 reproduce.sh。

该任务评估判定与人工评分的一致性，保留官方标签极性、节点规则和聚合方式，单独报告其官方 F1。它与 ArtiCheck-Claims 的“缺陷为正类、正负类 F1 取平均”口径不同，不将两种 F1 合并计算。

部分 submission 需按官方脚本获取。比较时应固定评分输入、上下文与工具权限。JudgeEval 的结果按 rubric 节点报告，PaperBench 的独立复跑成绩另行报告。

### 公开 CPU 案例

LIBLINEAR Section 3.1 重构案例完成 3 个版本 × 5 个数据划分种子 = 15 次运行、60 个阶段。L2-SVM 准确率均值为 96.76%，样本标准差 0.31 个百分点；执行器耗时 147.41 秒，包含审计、构建与运行。归档来源是 [CI](https://github.com/Gump111458785/ArtiCheck/actions/runs/40889691677)，偏差和执行方式见 [案例说明](../examples/liblinear_case/README.md)。

这衡量执行链路，不是主张缺陷检测、Planner 训练或正式外部 benchmark 成绩。原论文划分未找回，现代代码、额外固定参数控制与原论文不完全相同；未覆盖的 Figure 1 / rcv1 / 外部求解器继续列为缺口。不同数据划分的配对 bootstrap 只适用于所声明协议，不表示原论文的所有统计结论成立。

## 3. 模型对照与公开结果范围

公开归档包含上面的受控样例与 CPU 复现案例。完整模型对照按固定的模型版本、任务快照、采样预算和工具权限进行。模型对照成绩、外部基准汇总和私有数据未随此仓库发布。

| 对照 | 测量目的 |
|---|---|
| FixedPlanner 与确定性规则 | 工程链路和可控缺陷基准 |
| 外部 Paper Reproducibility Agent | 业务复现流程 |
| 单 Agent 与固定工作流 | 工作流分解对取证与判定的影响 |
| SFT Planner | 教师轨迹蒸馏的收益 |
| GRPO Planner | 实验选择和停止策略的收益 |

对照固定模型、任务、工具、上下文、硬件和预算。消融分别切换误报惩罚、成本项、课程阶段、高侧裁剪、动态补采样和重要性修正。

## 4. 指标与发布规则

- **主张判定：** ArtiCheck-Claims 以缺陷为正类。宏 F1 对正负两类的 F1 取平均。记录召回率、误报率、样本支持数与弃权率；缺失数据和运行失败不自动作为缺陷正例。
- **误报约束：** 在验证集选择阈值并冻结，然后评价测试集。如果测试集误报率超过 5%，必须报告约束未满足，不能只报告召回率。当前规则 score 为 0/1，不能视为模型概率。
- **外部基准：** 保存官方评测器版本、原始结果和任务清单。对协议或工具权限的修改必须披露；改编版本不作为官方可比成绩。
- **时延：** 同一硬件报告中位数与 P95，分别测冷启动和缓存命中。未检查主张与任务失败保留在结果中，防止通过提前停止获得虚假的速度优势。
- **成本：** 保存输入/输出 token、API 单价、GPU 使用时长与计价方式。硬件租赁、模型服务、环境准备的计价范围一致；默认 API 单价为 0 的当前样例不算真实成本实验。
- **重复与不确定性：** 正式模型实验计划至少 3 个随机种子；主张指标按原始仓库做聚类 bootstrap，报告置信区间。复现任务的相关难度版本也需按同源论文保留相关性，不能假设全部独立。
- **结果归档：** 发布结果前保存数据版本、split、模型与策略版本、采样参数、预算、硬件、逐任务结果及汇总脚本。每个实测条目需关联对应的数据版本、运行记录和结果文件。
