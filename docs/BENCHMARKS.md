# Benchmark 与结果协议

本文区分已经取得的工程验证结果与理想完成态的实验计划。公开 benchmark 适配、真实数据集和 GPU 训练尚未完成，目标值不是测量值。

## 1. 评测覆盖

### ArtiCheck-Claims：拟建的主张缺陷集

这是项目计划建设的任务集名称，目前没有正式发布的数据集。规划至少 50 个独立原始仓库、1,000 条人工审核后的实验主张，覆盖指标计算、训练/测试划分与 baseline 设置。数量属于建设目标，不能用于描述当前数据规模。

每个原始仓库保留经核验的 clean 版本，针对可判定缺陷建立注入版本，并收录能取得独立证据的真实问题。注入缺陷与自然缺陷分开报告；不能把注入实验结果直接解释为真实论文的缺陷发现能力。缺陷比例和难度分布在数据建成后统计，不预先宣称业务类别占比。

按原始仓库谱系分组，沿用当前 80/10/10 的划分协议。所有复制品、分支、注入版本与关联主张共享 repo_id；对同源数据不能通过改名获得独立测试样本。正式版本需保存 commit、probe、标签来源、审核记录和 split 清单，且需确保验证集与测试集均包含正负主张。

两名审核人独立标注，分歧由第三人裁定，是拟采用的质量流程，尚未执行。训练数据可包含经审核的教师轨迹；验证与测试真值只用于评测。

### CORE-Bench：公开的计算复现基准

[官方仓库](https://github.com/siegelz/core-bench)描述的规模为 90 篇科学论文、270 个任务。任务要求阅读说明、处理代码和依赖、运行实验并回答结果问题，适合衡量执行与结果读取能力。

计划按 Easy、Medium、Hard 分层，沿用官方 harness 的任务判定和结果聚合口径。原仓库推荐迁移至 [HAL Harness](https://github.com/princeton-pli/hal-harness)。当前 ArtiCheck 没有该适配器；若只运行子集，应显著注明任务 ID、数量和筛选标准，不能以完整 CORE-Bench 成绩发布。

该数据不直接给出“某实验主张是否存在科学缺陷”的标签。若额外注入缺陷，所得数据必须另命名为派生集，并独立核验真值，不能与原生 CORE-Bench 混为一谈。

### PaperBench JudgeEval：公开的判定质量基准

[JudgeEval 官方说明](https://github.com/openai/frontier-evals/tree/main/project/paperbench/paperbench/judge/judge_eval)提供 5 份带人工预期评分的 submission，在 rubric 二元节点上计算 accuracy、precision、recall 和 F1。它独立于 PaperBench 的复跑阶段；JudgeEval 本身不运行 reproduce.sh。

计划用该任务评估判定与人工评分的一致性，保留官方标签极性、节点规则和聚合方式，单独报告其官方 F1。它与 ArtiCheck-Claims 的“缺陷为正类、正负类 F1 取平均”口径不同，不将两种 F1 合并计算。

部分 submission 需要按官方脚本另行获取。适配器应先核对评分输入、上下文与工具权限，目前没有完成。运行 JudgeEval 不能表述为已完成 PaperBench 的 20 篇论文从零复现实验。

## 3. 理想完成态目标

这些目标由项目自行设定，用来规划验收，尚无实测或统计依据支持其已经可达。正式数据和预算确定后，应在查看测试结果之前冻结目标或记录修订。

| 范围 | 目标 |
|---|---|
| ArtiCheck-Claims | 宏 F1 ≥ 0.90 |
| ArtiCheck-Claims | 在误报率 ≤ 5% 时，问题召回率 ≥ 85% |
| CORE-Bench | 相比固定工作流 + 7B，任务成功率提升 ≥ 10 个百分点，按难度分别报告 |
| JudgeEval | 官方 F1 ≥ 0.85 |
| 时延 | 核查耗时中位数 ≤ 固定工作流 + 7B 的 70% |
| 成本 | 每篇成本 ≤ 固定工作流 + 7B 的 60%，且满足同一质量门槛 |

CORE-Bench 和 JudgeEval 的目标不代表它们已接入。没有为尚未运行的基线填入虚构的绝对分数，也没有 SFT 或 GRPO 的已测提升。

## 4. 拟比较的系统

| 系统 | 用途 | 当前状态 |
|---|---|---|
| FixedPlanner + 规则核查 | 工程可运行性对照 | 已实现并运行教学样例 |
| 外部 Paper Reproducibility Agent | 业务 baseline | 启动脚本与报告导入已提供；真实任务待运行 |
| 单 Agent + 7B 提示词 | 检验工作流分解的作用 | 待实现对照运行器 |
| 固定工作流 + 7B | 正式模型实验的主要基线 | 待实现固定模型调用对照；当前 FixedPlanner 不调用 7B |
| SFT Planner + 7B | 检验教师轨迹蒸馏效果 | 训练基础代码已提供；待 GPU 实验 |
| GRPO Planner + 7B | 检验实验选择和停止策略优化 | AgentLoop 与配置已提供；待 GPU 集成与实验 |

模型实验使用相同基础模型 revision、任务快照、工具权限、上下文限制、硬件和预算。消融拟覆盖误报惩罚、成本项、课程阶段、clip-higher、动态采样与 IS；每次只改变被消融因素。

## 5. 指标与发布规则

- **主张判定：** ArtiCheck-Claims 以缺陷为正类。宏 F1 对正负两类的 F1 取平均。记录召回率、误报率、样本支持数与弃权率；缺失数据和运行失败不自动作为缺陷正例。
- **误报约束：** 在验证集选择阈值并冻结，然后评价测试集。如果测试集误报率超过 5%，必须报告约束未满足，不能只报告召回率。当前规则 score 为 0/1，不能视为模型概率。
- **外部基准：** 保存官方评测器版本、原始结果和任务清单。对协议或工具权限的修改必须披露；改编版本不作为官方可比成绩。
- **时延：** 同一硬件报告中位数与 P95，分别测冷启动和缓存命中。未检查主张与任务失败保留在结果中，防止通过提前停止获得虚假的速度优势。
- **成本：** 保存输入/输出 token、API 单价、GPU 使用时长与计价方式。硬件租赁、模型服务、环境准备的计价范围一致；默认 API 单价为 0 的当前样例不算真实成本实验。
- **重复与不确定性：** 正式模型实验计划至少 3 个随机种子；主张指标按原始仓库做聚类 bootstrap，报告置信区间。复现任务的相关难度版本也需按同源论文保留相关性，不能假设全部独立。
- **结果归档：** 发布结果前保存数据版本、split、模型与策略版本、采样参数、预算、硬件、逐任务结果及汇总脚本。训练结果和理想目标应保留各自明确的标题，不能在未运行时把目标改写成已取得结果。
